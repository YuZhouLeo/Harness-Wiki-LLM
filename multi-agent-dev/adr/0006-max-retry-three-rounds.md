# ADR-0006: max retry = 3（兩個驗證階段共用）

- 狀態：Accepted
- 日期：2026-05-06

## 脈絡

[plans/多代理協作工作流計劃.md](C:/Users/yuzho/.claude/skills/multi-agent-dev/spec/多代理協作工作流計劃.md) 的兩個驗證階段都需要設**上限輪數**，超過上限即觸發交棒（advisor-stuck MD / handoff MD）。需要決定這個上限值。

兩個階段的本質：

- **計劃顧問協商**（[ADR-0003](0003-split-plan-advisor-and-impl-validator.md)）：諮詢式來回，目標是達成共識
- **實作驗證**（[ADR-0003](0003-split-plan-advisor-and-impl-validator.md)）：對抗式守門，目標是 PASS

兩種互動模式不同，但**「上限應該設多少」的取捨邏輯一致**：

| 太少（1–2 輪） | 太多（≥ 5 輪 / 無限） |
|---|---|
| 提早放棄可能即將收斂的問題 | Token 浪費、節奏拖慢 |
| 假陽性 handoff 過多，使用者疲於裁決 | 真的 stuck 的問題拖很久才暴露 |
| Codex 第一輪建議常包含「值得討論」的點，立刻砍掉就浪費 | 多輪後通常已經繞圈，不會收斂 |

實務經驗上（其他 multi-agent 系統的觀察）：

- **第 1 輪**通常含結構性建議與雜訊
- **第 2 輪**雜訊被過濾，剩下的多是真爭議
- **第 3 輪**仍卡住代表「規劃 / 實作標準與 Codex 標準有結構性歧異」，再多輪也不會自動收斂——此時人類仲裁的邊際價值最高

統一兩個階段用相同上限（而非協商 5 輪、驗證 3 輪這類差異化設定）的好處：

- 主代理調度邏輯簡單：一個常數
- 使用者預期一致：兩條交棒路徑都是「3 輪後會看到 MD」
- 開放問題 §9 #7 已使用者親自確認「3 輪起步，Phase 2 觀察後再調」

## 決策

兩個驗證階段（計劃顧問協商 / 實作驗證）的 max retry **皆設為 3**。

### 規則

1. **計劃顧問協商**：最多 3 輪完整來回（一輪 = 顧問建議 → 規劃回應 → 顧問再評估）。第 3 輪後仍互不退讓 → 寫 `plans/<功能名>計劃-advisor-stuck-<時間戳>.md`（[plans/多代理協作工作流計劃.md](C:/Users/yuzho/.claude/skills/multi-agent-dev/spec/多代理協作工作流計劃.md) §3.2.1）
2. **實作驗證**：最多 3 輪修正。第 3 輪後仍 FAIL → 寫 `plans/<功能名>-handoff-<時間戳>.md`（[plans/多代理協作工作流計劃.md](C:/Users/yuzho/.claude/skills/multi-agent-dev/spec/多代理協作工作流計劃.md) §3.2.2）
3. **交棒後主代理立刻停手**：寫完 stuck/handoff MD 即回報使用者「已交棒至 `<路徑>`，請裁決」；不再嘗試任何修正、不再呼叫任何子代理
4. **Phase 2 觀察條件**（[plans/多代理協作工作流計劃.md](C:/Users/yuzho/.claude/skills/multi-agent-dev/spec/多代理協作工作流計劃.md) §9 #7）：若前 5 個任務 ≥ 30% 跑滿 3 輪才收斂（即「在第 3 輪剛好 PASS / 共識」而非「2 輪內就好」），代表上限太緊，放寬到 5 輪。本 ADR 預設先以 3 輪起步

評估過的替代：

- **5 輪**：給更多收斂空間，但 token 成本明顯提升、Phase 2 還沒驗證需求就先過度供給。**否決**——Phase 1 起步應該守緊，需要時再放寬
- **無限（handoff 永不觸發）**：信任迴圈最終會收斂。**否決**——已知有「Codex 標準漂移」「計劃規格不清」「實作來回拉扯」三類結構性僵局，不會自動解
- **協商 5 輪 / 驗證 3 輪（差異化）**：理論上協商比對抗更需要時間。**否決**——複雜化主代理邏輯，且 Phase 1 沒有實證資料支持差異化
- **依任務複雜度動態決定上限**：理想，但「複雜度」沒有可量化指標，主代理自己評估會有偏差。**否決**——Phase 2 觀察後若需要再考慮
- **第 1 輪不算上限，從第 2 輪開始計**：含義是「第 1 輪建議是免費的，從修正開始計」。**否決**——增加邏輯複雜度，且第 1 輪的駁回 / 建議本就是有效輪次

## 後果

**好處**

- 主代理調度邏輯極簡：一個常數 `MAX_RETRY = 3`
- 使用者預期一致：兩條交棒路徑都是「3 輪後會看到 MD」
- 守緊起步，避免 Phase 1 過度供給：Phase 2 有實證資料後再放寬
- 統一上限便於主代理實作（[plans/多代理協作工作流計劃.md](C:/Users/yuzho/.claude/skills/multi-agent-dev/spec/多代理協作工作流計劃.md) §6 Phase 1.5 已預期此後果）

**壞處**

- **可能在「即將收斂的第 4 輪」被切斷**：尤其是計劃顧問協商，第 3 輪雙方剛好開始妥協，第 4 輪就會達成共識——但被上限砍掉。Phase 2 觀察期就是在量這個（緩解：§7 #7 已預設「≥ 30% 任務跑滿 3 輪才收斂」即放寬條件）
- **handoff MD 可能初期暴增**：若實際需要 4–5 輪，3 輪上限會頻繁觸發 handoff，使用者疲於裁決（接受——這正是 Phase 2 要量化的訊號；handoff 本身有完整對答歷史，使用者可一次裁決多筆）
- **對複雜任務不夠用**：跨多模組重構這類任務本來就需要更多協商，3 輪可能太緊（緩解：使用者可在 advisor-stuck MD 勾「採用規劃方案」直接收斂；不需要重啟工作流）

**需要持續觀察**

- Phase 2 前 5 個任務的「實際收斂輪數分布」：若大多數 1–2 輪內收斂，3 輪上限合理；若 ≥ 30% 跑滿 3 輪，本 ADR 需被新 ADR supersede 為「max retry = 5」
- 計劃顧問協商與實作驗證的「實際收斂輪數差異」：若協商總是 1 輪、驗證總是 3 輪，可能要差異化上限（但需新 ADR）
- Handoff MD 觸發後使用者實際選的選項分布：若大部分選「採用規劃方案」（即覆蓋 Codex 否決），代表上限太緊或 Codex 太嚴格——需重新評估
- 主代理「立刻停手」規則的遵守度：若有任何一次主代理在 handoff 後仍嘗試修正，需在系統提示加更強硬的禁止規則（[plans/多代理協作工作流計劃.md](C:/Users/yuzho/.claude/skills/multi-agent-dev/spec/多代理協作工作流計劃.md) §7 風險表第 9 條）
