# ADR-0004: 經驗資料庫採三大寫入原則

- 狀態：Accepted
- 日期：2026-05-06

## 脈絡

[plans/多代理協作工作流計劃.md](C:/Users/yuzho/.claude/skills/multi-agent-dev/spec/多代理協作工作流計劃.md) 設計的工作流在每輪 PASS 終局會由 `lesson-keeper` 把「本輪 Codex 駁回理由」蒸餾成可遷移的經驗條目，追加到 [wiki/lessons.md](wiki/lessons.md)。下一輪 planner / executor 開工前先 grep 同類條目，避免重複踩坑。

但「沉澱經驗」這件事有兩個典型的失敗模式，會直接讓資料庫從資產退化成負債：

### 失敗模式 1：過度具體（資料庫變廢墟）

把 Codex 駁回的「具體錯誤」原文搬進條目：

> 焦點卡片 shimmer 用 `rgba(217,119,87,0.12)` 而不是 `rgba(255,255,255,0.06)`

這條只對「下次又寫到這個顏色變數」的場景有用。換個專案、換個元件、甚至同專案換個頁面就無效。資料庫 50 條後 grep 命中率歸零，沒人讀，變廢墟。

### 失敗模式 2：假深度（廢話包裝成原則）

把通用詞包裝成「原則」：

> 寫 code 要遵守最佳實踐
> UI 要符合設計系統

這種條目零資訊量。讀者讀完不知道「為什麼錯」「什麼時候該用」「什麼時候不該用」，沒辦法遷移到下次決策。資料庫 50 條後變說教文集，沒人讀，變廢墟。

兩個失敗模式都會讓資料庫**從資產退化成負債**：planner / executor 不僅學不到東西，還要花時間 grep 過所有無效條目。**自由格式不行，但嚴格 schema 又會讓 lesson-keeper 寫不出來**——這個 trade-off 必須用「寫入原則」而非「欄位約束」來解。

## 決策

採用 **三大寫入原則**作為 lesson-keeper 寫入時的硬規則，並配套**自我檢查清單**強制執行。

### 三大原則

**原則 1：原則性 > 數值性**
寫「為什麼錯」，不寫「這次改了哪個值」。

| 反例（不要寫） | 正例（要寫成這樣） |
|---|---|
| 焦點卡片 shimmer 用 `rgba(217,119,87,0.12)` | accent 色卡片的自訂微光應該和邊框色系一致 |

**原則 2：模式級 > 頁面級**
寫「哪種布局/架構模式容易犯這個錯」，不寫「某頁面要怎麼改」。

| 反例（不要寫） | 正例（要寫成這樣） |
|---|---|
| VS 對比頁左右欄要用面對面原則 | 對欄對比布局中，兩欄應朝分割線對齊（面對面），而非朝容器中心對齊 |

**原則 3：可遷移 > 可複製**
下個專案題材完全不同時，這條經驗是否還有用？沒用就不要寫。

| 反例（不要寫） | 正例（要寫成這樣） |
|---|---|
| page14 的階梯級 CSS class 要通用 | 可復用的視覺組件應該使用 CSS class（而非 inline style） |

### 自我檢查清單（lesson-keeper 寫入前必跑）

對每一條候選條目逐項打勾，任一項打不出勾就**重寫或丟棄**：

- [ ] 這條原則替換成另一個專案、另一種題材後，文字本身仍成立嗎？
- [ ] 條目中是否出現具體數值（hex 色碼、px 數字、檔案路徑、變數名）？若是，能否抽象掉？
- [ ] 條目是否提到「這頁」「這個元件」「page14」這類專案級指涉？若是，能否改寫成「這類布局」「這類元件」？
- [ ] 「為什麼」段是否解釋了**根因**（為什麼這樣才對），而非只重述「就是這樣寫」？
- [ ] [wiki/lessons.md](wiki/lessons.md) 中是否已有同原則條目？若有，改去那條下面加 `相關案例:`，不要新開條目

### 寧缺勿濫

「本輪 0 條可萃取」是**合法結果**——若本輪 Codex 從第一輪就 PASS、或修正內容只是純 typo 級錯字、或駁回理由抽不出原則級結論，**寧可不寫**，也不要為了交差寫廢話進資料庫。詳見 [plans/多代理協作工作流計劃.md](C:/Users/yuzho/.claude/skills/multi-agent-dev/spec/多代理協作工作流計劃.md) §3.3。

評估過的替代：

- **自由格式（無寫入規範）**：lesson-keeper 想怎麼寫就怎麼寫。短期 friction 最低，但失敗模式 1 + 2 同時觸發，3 個月後資料庫變廢墟。**否決**——這是要避免的反模式
- **嚴格 schema（強制每條 N 個欄位）**：規範清楚，但 lesson-keeper 為了填欄位會把不該抽象的東西強行抽象，或寫廢話充數。**否決**——「有規範但寫不出」比「沒規範亂寫」更糟
- **每條都要 PR review 才能合併**：人類把關品質。**否決**——把 lesson-keeper 的價值（自動化沉澱）抹掉，且 review burden 落在使用者身上
- **只記錄駁回原文，不嘗試蒸餾**：誠實但失去資料庫的核心價值——可遷移性。**否決**——下個專案 grep 不到任何有用內容
- **混合制（原則性條目 + 駁回原文 archive）**：本 ADR 預設「原則性條目」即正規入口；若實作後發現「駁回原文歸檔」也有獨立價值，可在 Phase 3 補一份 ADR 補充

## 後果

**好處**

- 資料庫條目 100% 可遷移：planner / executor 在任何新任務都能 grep 到有用內容
- 「寧缺勿濫」原則保護資料庫純度：條目少而精，命中率高
- 自我檢查清單讓 lesson-keeper 的判斷有具體依據，不靠主觀感覺

**壞處**

- **lesson-keeper 必須用 Sonnet 級推理**：抽象 + 篩選的工作 Haiku 容易把「數值性錯誤」直接寫進去（緩解：[lesson-keeper.md](C:/Users/yuzho/.claude/agents/lesson-keeper.md) frontmatter 鎖死 `model: sonnet`，禁止降級）
- **0 條結果頻率可能很高**：若 Codex 駁回多是「typo 級」或「規範細節」，lesson-keeper 一直回 0 條，資料庫成長緩慢（接受——0 條優於假深度）
- **使用者初期需校準標準**：首批 10 條條目寫入後，使用者親自審查一次，確認 lesson-keeper 對「原則性 > 數值性」的理解是否與設計者一致（[plans/多代理協作工作流計劃.md](C:/Users/yuzho/.claude/skills/multi-agent-dev/spec/多代理協作工作流計劃.md) §7 風險表第 14 條）

**需要持續觀察**

- 條目實際被 grep / 引用的頻率：Phase 2 結束時若 < 20% 條目被引用過，需重新檢討「可遷移性」的標準是否太鬆
- lesson-keeper 寫入時違反原則的頻率：若超過 30% 候選條目被自我檢查清單駁回，代表系統提示要更強硬
- 50 條後分檔的時機：依 [plans/多代理協作工作流計劃.md](C:/Users/yuzho/.claude/skills/multi-agent-dev/spec/多代理協作工作流計劃.md) §3.4.1 由 lesson-keeper 自行提案分檔
