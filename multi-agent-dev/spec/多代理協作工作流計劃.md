# OpenStock 多代理協作工作流計劃

> **狀態**：草案 v0.2（2026-05-06）
> **目標讀者**：使用者本人 + 未來實作此工作流的 Claude Code 主代理
> **Git 政策**（§9 #4 已確認）：
> - **commit**：本計劃書、`wiki/lessons.md`、`plans/*-handoff-*.md`、`plans/*-advisor-stuck-*.md`、`wiki/runs/INDEX.md`
> - **不 commit**（加進 `.gitignore`）：`wiki/runs/<時間>-*.md`（單一 run 的完整日誌，每次跑都產生，見 §3.5）

---

## 1. 背景與目標

OpenStock 目前的開發流程是「人 ↔ 單一 Claude Code 主對話」。隨著功能變複雜，下列問題逐漸浮現：

- 主對話 context window 被「規劃 + 驗證 + 執行 + 修錯」全塞在一起，token 成本高、上下文容易污染
- 規劃時用的脈絡與執行時用的脈絡互相干擾，常導致「邊規劃邊改實作」的混亂
- 沒有獨立的「驗證者」視角，主對話自己寫自己審，盲點多
- **每次踩到的坑都重複踩**：本輪 Codex 駁回的理由、本輪 planner / executor 學到的教訓，下一輪換個任務又從零開始；經驗無法累積

本計劃導入 **orchestrator-worker（主代理-子代理）** 模式，配合 **同身份重入修錯（context retention via SendMessage）** 機制，將開發流程切成六個明確角色（主代理 / 規劃 / **計劃顧問**(Codex 諮詢模式) / **實作驗證**(Codex 對抗模式) / 執行 / 經驗），由主代理純調度、子代理專責執行；每輪 PASS 終局時由經驗代理把通用教訓沉澱進經驗資料庫，下一輪自動查閱。

> 兩個 Codex 角色刻意拆開：**計劃顧問**負責提建議（規劃代理有最終決定權，但需說服顧問才能保留原方案），**實作驗證**負責守門（PASS/FAIL，3 輪不過直接 handoff）。同個 Codex 後端，不同 prompt template，不同 session，不同終局規則。

### 核心原則

| 原則 | 說明 |
|------|------|
| **主代理零生產** | 主代理**不開發、不閱讀程式碼、不執行命令**。只做：分派、收檔案位置、傳遞訊息、判斷迴圈是否結束 |
| **誰寫的誰修** | 驗證若不通過，**由原本產出該檔案的子代理**重寫——因為他有當時的判斷上下文 |
| **誰驗的誰續驗** | 同一份檔案的多輪驗證，**由同一個驗證代理實例**繼續，避免重複建立評審基準 |
| **檔案是唯一交付物** | 子代理之間不直接對話，全部透過「檔案位置」交換成果 |
| **經驗會沉澱** | 每輪 PASS 後，本輪「為什麼錯」蒸餾為可遷移的原則，寫進 `wiki/lessons.md`；下一輪 planner / executor 開工前先 grep 一次，避免重複踩同類坑 |

## 2. 角色定義

### 2.1 主代理（Orchestrator，主對話本身）

- **位置**：使用者開啟的 Claude Code 主對話，不是 subagent 檔案
- **職責**：
  1. 接收使用者需求
  2. 呼叫 `planner-agent` → 拿到計劃書檔案路徑
  3. **計劃顧問協商階段**：呼叫 **Plan-Advisor**（`/codex:review --background <計劃書>` 帶諮詢模式 prompt）→ 收建議清單 + advisor-session-id
  4. SendMessage 把建議清單交給 `planner-agent` → 收採納/不採納決策（每條附理由）
  5. 把規劃代理回應轉交顧問（`/codex:review --resume <advisor-session-id>`）→ 收顧問回應（接受反駁 / 再反駁 / 新建議）
  6. 重複 4–5 直到所有建議達成共識；**共識達成 = 計劃書通過**。中途 `planner-agent` 採納的建議要先 SendMessage 請他改寫計劃書；未採納但顧問接受的建議要請他在「架構決策」段補記「曾考慮 X，不採用因為 Y」
  7. **實作階段**：呼叫 `executor-agent` → 拿到實作檔案路徑清單 + lint/test 輸出
  8. 呼叫 **Impl-Validator**（`/codex:adversarial-review --background <實作檔>` 帶對抗模式 prompt，**新開 session，不要 resume advisor session**）→ 收結果 + impl-session-id
  9. FAIL：用 SendMessage 把同一個 `executor-agent` 喚醒，丟 Codex 理由給他修；重審用 `/codex:adversarial-review --resume <impl-session-id>`，回到步驟 8
  10. PASS：呼叫 `lesson-keeper` → 萃取本輪通用經驗到 `wiki/lessons.md` → 收他回報「新增 N 條」
  11. 回報使用者「完成 + 新學到 N 條經驗」並列出產出檔案
  12. **計劃顧問協商 3 輪仍無共識** → 寫 `plans/<功能名>計劃-advisor-stuck-<時間戳>.md`（§3.2.1）；**實作驗證 3 輪仍 FAIL** → 寫 `plans/<功能名>-handoff-<時間戳>.md`（§3.2.2）。任一觸發 → 交棒使用者，立刻停止調度（**兩條交棒路徑都不自動觸發 lesson-keeper**，理由見 §3.3）
- **絕對禁止**：
  - 自己讀任何 source code 或計劃書內容（觸發 §3.2 handoff 條件除外，且僅為整理對答歷史用）
  - 自己跑命令（`npm`、`git`、測試……一律由 executor 跑；Codex review 不算「跑命令」，是調度）
  - 自己做技術判斷（架構好不好、套件選對沒——一律交給 Codex 驗證）
- **可做**：
  - Read 子代理回傳的「**摘要訊息**」與 Codex 回傳的 PASS/FAIL 理由
  - 記錄 Codex session-id（advisor + impl）並在後續輪次傳入對應 `--resume`
  - **Write Run Log**（`wiki/runs/<時間>-<功能>.md`，§3.5 規範）：每次子代理回應 / Codex 回傳時同步追加一行
  - **Write Handoff / Advisor-stuck MD**：觸發 §3.2.1 / §3.2.2 條件時

### 2.2 規劃代理（Planner Subagent）

- **檔名**：`.claude/agents/planner.md`
- **職責**：根據主代理傳入的需求，撰寫一份完整計劃書到 `plans/<功能名>計劃.md`，回傳檔案絕對路徑
- **產出規格**（計劃書必含）：
  - 需求拆解（user story / acceptance criteria）
  - 架構決策（選哪個層、為何放在 lib/actions 還是 app/api）
  - 套件選擇（已有的優先；新引入要寫理由 + 替代方案比較）
  - 影響檔案清單（哪些要新增、哪些要改、哪些要刪）
  - 測試策略
  - 風險與回滾計劃
- **工具**：`Read, Glob, Grep, Write, Edit`（禁用 Bash、避免規劃時跑指令）
- **模型**：Sonnet（規劃需要推理）
- **修改場景**：被主代理用 SendMessage 喚醒時，會收到「計劃顧問的建議清單」（§2.3），需逐條決定採納/不採納，並為「不採納者」寫**能說服顧問**的反駁理由；對「採納」者要實際改寫計劃書，非僅口頭同意

### 2.3 計劃顧問代理（Plan-Advisor = Codex 諮詢模式）

- **不是 Claude subagent**：由 Codex 透過 [codex-plugin-cc](https://github.com/openai/codex-plugin-cc) 擔任；獨立 session，**與 §2.4 實作驗證代理的 session 完全不共享上下文**
- **角色定位**：諮詢者，**不是守門員**。提出更優建議＋理由，由規劃代理決定採納與否
- **職責**：審查計劃書，從三個面向提出更優建議：
  - **架構**：選擇的層次（`lib/actions` / `app/api` / `lib/inngest`）對需求是否最自然；OpenStock 既有 invariants 是否被破壞
  - **語法 / 慣用法**：TypeScript / React / Next.js App Router 當前最佳寫法；是否有過時模式
  - **工具 / 套件**：是否有更輕、更穩、或已存在於 `package.json` 的替代方案
- **協商互動流程**（共識，非裁決）：
  1. 顧問讀計劃書，產出「建議清單」：每條 = 建議內容 + 理由 + 替代方案比較
  2. 主代理把建議清單轉交規劃代理（SendMessage）
  3. 規劃代理逐條決定 **採納 / 不採納**；不採納者必須寫反駁理由
  4. 主代理把規劃代理回應轉交顧問（`/codex:review --resume <session-id>`）
  5. 顧問收到後三選一：
     - **接受規劃代理的反駁** → 該條共識達成
     - **提出更具體的反駁** → 回到 step 3
     - **新發現另一條建議** → 加入清單，回到 step 3
  6. 重複 2–5 直到「所有建議都已達成共識」（採納或顧問接受不採納）
- **產出物**（每輪都更新）：
  - **`plans/<功能名>計劃-advisor.md`**：append-only audit log，記錄每一輪建議＋反駁＋共識結果（顧問端的對答歷史）
  - **`plans/<功能名>計劃.md`**：規劃代理依採納結果改寫；未採納但已說服顧問的建議，在「架構決策」段補上「曾考慮 X，不採用因為 Y」
- **終局規則**：最多 **3 輪**完整來回協商（與實作驗證上限一致；§9 #7 已確認此值，Phase 2 觀察後若 ≥ 30% 任務跑滿 3 輪才收斂則放寬到 5 輪）。第 3 輪後仍互不退讓 → 主代理寫 `plans/<功能名>計劃-advisor-stuck-<時間戳>.md` 交棒使用者裁決，不再續迴圈
- **重要**：顧問**不直接改計劃書**——只提建議；改寫永遠由規劃代理執行（保持「誰寫的誰修」原則）

### 2.4 實作驗證代理（Impl-Validator = Codex 對抗模式）

- **不是 Claude subagent**：由 Codex 擔任，但**與 §2.3 計劃顧問代理的 session 完全分離**——不同 session-id、不同 prompt template、不同終局規則
- **角色定位**：守門員，PASS / FAIL 二擇一裁決
- **職責**：審查實作檔案是否：
  - 照計劃實作（沒擅自加料、沒改未列出的檔案）
  - 遵守 conventions（[docs/conventions/](../docs/conventions/) 與 [AGENTS.md](../AGENTS.md) §Invariants）
  - 測試覆蓋 acceptance criteria
  - `npm run lint` / `npm test` 通過（由 executor 跑完後把輸出附到 prompt，**Codex 不自己跑 Bash**）
- **指令**：呼叫 `/codex:adversarial-review`，prompt 內附上計劃書路徑（含 §2.3 階段達成的所有共識）做對照
- **同身份重入機制**：`--background` 啟新 session 取得 session-id；後續輪次 `--resume <session-id>`
- **終局規則**：3 輪仍 FAIL → 主代理寫 `plans/<功能名>-handoff-<時間戳>.md`（§3.2.2 規範）
- **重要**：Impl-Validator 不寫程式、不改檔案，只回報 PASS / FAIL + 理由原文；修正交回給執行代理

### 2.5 執行代理（Executor Subagent）

- **檔名**：`.claude/agents/executor.md`
- **職責**：依計劃書檔案路徑，實際撰寫程式碼、執行測試，回傳產出檔案清單
- **流程**：
  1. Read 計劃書全文
  2. 按計劃寫 / 改檔案
  3. 跑 `npm run lint` 和 `npm test` 自我檢查
  4. 回傳：「已修改檔案列表 + 測試結果摘要」
- **工具**：`Read, Glob, Grep, Write, Edit, Bash`（全工具）
- **模型**：Sonnet 起步；穩定後可降 Haiku 試試
- **修改場景**：被 SendMessage 喚醒時收到 Codex 的具體反對點，只改該點，不重寫無關檔案

### 2.6 經驗代理（Lesson-Keeper Subagent）

- **檔名**：`.claude/agents/lesson-keeper.md`
- **觸發時機**：工作流走到 **PASS 終局**（實作驗證通過、回報使用者前）；handoff 路徑**不自動觸發**（由使用者決議後手動呼叫，理由見 §3.3）
- **職責**：把本輪「Codex 駁回理由 + planner/executor 修正動作」蒸餾成可遷移的經驗條目，追加到經驗資料庫 [wiki/lessons.md](../wiki/lessons.md)
- **三大寫入原則**（嚴格守護，違反者重寫；詳細定義見 §3.4）：
  1. **原則性 > 數值性**：寫「為什麼錯」而非「這次改了哪個值」
  2. **模式級 > 頁面級**：寫「哪種布局/架構模式容易踩」而非「某頁面要怎麼改」
  3. **可遷移 > 可複製**：下個專案題材完全不同時，這條經驗仍要有用
- **流程**：
  1. Read 本輪計劃書、實作檔 diff、各輪 Codex review 理由
  2. Read 現有 [wiki/lessons.md](../wiki/lessons.md)，避免重複條目（同原則只留一條，可在原條目下加 `相關案例:` 連結本輪計劃書）
  3. 套用三大原則篩選：能寫成原則級就寫，寫不出原則級就**寧缺勿濫**（回傳「本輪無可萃取的通用經驗」也是合法結果）
  4. Edit 追加 0–N 條新條目（格式見 §3.4），同時在檔頂索引補上 anchor
  5. 回報主代理：「新增 N 條經驗，分別是 ...」
- **工具**：`Read, Glob, Grep, Bash, Edit, Write`（Bash 只用於 `git diff` / `git log` 等唯讀指令；Write 只用於第一次建立 lessons.md）
- **模型**：Sonnet（需要抽象與篩選；Haiku 容易把「數值性錯誤」直接寫進去）
- **絕對禁止**：
  - 不准改任何程式碼或計劃書
  - 不准複製本輪修正的具體 diff 進經驗條目（那違反原則 1）
  - 不准只憑「程式碼這次這樣寫」就推斷原則；必須有 Codex 駁回理由作為原則的「為什麼」依據

### 3.1 為什麼用 SendMessage / `--resume` 而非重新啟動

Claude Code 的 Agent tool 文件明確說明：

> To continue a previously spawned agent, use SendMessage with the agent's ID or name as the `to` field — that resumes it with full context. A new Agent call starts a fresh agent with no memory of prior runs.

這正好對應使用者要的「**出錯的代理因為有上下文，由他來修**」。Claude subagent（planner / executor）只在第一次被呼叫時用 `Agent(...)` 啟動，之後**全程用 SendMessage 續任**。

Codex 走平行機制：第一輪用 `--background` 取得 session-id，後續輪次用 `--resume <session-id>` 接續同一個 session 的記憶，避免每輪冒出新的評審準則。

**注意**：一次完整工作流會產生**兩個獨立的 Codex session**——`advisor-session-id`（§2.3 計劃顧問協商用）與 `impl-session-id`（§2.4 實作驗證用）。兩者**絕對不可互相 resume**：advisor 不應該看到 lint/test 輸出，impl-validator 不應該收到「請提建議」的 prompt（見 §4.2.4）。

### 3.2 失敗迴圈的終止條件（修正版）

兩個驗證階段有不同的終局規則，因為互動模式不同（協商 vs 裁決）。

#### 3.2.1 計劃顧問協商：3 輪無共識 → advisor-stuck MD

**最多 3 輪完整來回協商**（一輪 = 顧問建議 → 規劃回應 → 顧問再評估）。第 3 輪後仍互不退讓，主代理停止協商，寫 advisor-stuck MD 交付使用者：

- **檔案位置**：`plans/<功能名>計劃-advisor-stuck-<YYYYMMDD-HHmm>.md`
- **必含內容**：
  1. 原始需求
  2. 計劃書當前版本路徑
  3. 全部建議清單，逐條附：顧問初始建議＋理由 / 規劃代理採納或反駁＋理由 / 顧問再回應 / ...（**完整對答歷史，不要摘要**）
  4. 仍無共識的爭議點（哪幾條建議卡住）
  5. 主代理建議的下一步選項（給使用者勾選）：
     - [ ] **採用顧問方案**（主代理請規劃代理依顧問建議改寫計劃書）
     - [ ] **採用規劃方案**（主代理請規劃代理在計劃書補上「曾考慮 X，不採用因為 Y」記錄，計劃書視為通過）
     - [ ] **改需求**（使用者修改原始需求，整個工作流重啟）
     - [ ] **退回規劃**（使用者親自和規劃代理對話釐清，跳過顧問）

#### 3.2.2 實作驗證：3 輪 FAIL → handoff MD

**最多 3 輪修正**。第 3 輪後仍 FAIL，主代理停止迴圈，將整段歷史整理成 handoff MD：

- **檔案位置**：`plans/<功能名>-handoff-<YYYYMMDD-HHmm>.md`
- **必含內容**：
  1. 原始需求 + 計劃書（含 §3.2.1 階段達成的所有共識）路徑
  2. 第 1～3 輪實作版本（路徑 + 主要差異摘要）
  3. 每一輪 Impl-Validator 的 FAIL **完整理由原文**
  4. 每一輪 executor 的修改說明
  5. 主代理觀察到的僵局類型：
     - 同一條理由反覆出現？→ Codex 標準與計劃本意歧異，需人類仲裁
     - 每輪冒出新理由？→ Codex 標準漂移，建議重啟 impl session
     - 實作來回拉扯？→ 計劃可能不夠具體，回頭補規格
  6. 主代理建議的下一步選項：
     - [ ] **放行**（覆蓋 Codex 否決，直接接受第 3 輪產出）
     - [ ] **改規格**（回規劃階段重來）
     - [ ] **人工接手實作**（Claude 都不動，使用者直接動手）
     - [ ] **重啟工作流**（清空 session，從頭跑一次）

#### 3.2.3 共通規則

- **交棒後主代理立刻停手**：寫完 stuck/handoff MD 即回報使用者「已交棒至 `<路徑>`，請裁決」。**不再嘗試任何修正、不再呼叫任何子代理**，等待使用者明確指示
- **兩條交棒路徑都不自動觸發 lesson-keeper**（理由見 §3.3）

> 移除舊版「兩輪同錯立刻終止」的提早結束規則。使用者明確選擇「跑滿 3 輪再交棒」，避免提早放棄可能即將解決的問題

### 3.3 工作流終局：經驗萃取（PASS 路徑專屬）

PASS 終局的最後一步是呼叫 `lesson-keeper`：

- **時機**：實作 Codex review 回 PASS 之後、主代理回報使用者之前
- **輸入**：本輪計劃書路徑、實作檔清單、執行代理回傳的測試輸出、**所有輪次 Codex 的 PASS/FAIL 理由原文**
- **產出**：追加到 [wiki/lessons.md](../wiki/lessons.md) 的 0–N 條新條目
- **「0 條」是合法結果**：如果本輪 Codex 從第一輪就 PASS、或修正內容只是純 typo 級錯字，沒有可遷移的「為什麼錯」可萃取——寧可不寫，也不要為了交差寫廢話進資料庫

**為何 handoff 路徑不自動觸發**：3 輪都 FAIL 代表「本輪沒有得出共識的修正方向」，此時自動萃取容易把「Codex 與 planner/executor 的分歧」當成原則寫進去——但分歧本身可能正是 Codex 標準漂移、或計劃本身規格不清。因此 handoff 後應由**使用者讀完 handoff MD、做完裁決**，再決定是否手動呼叫 `lesson-keeper`，並明示是從哪個視角萃取（「Codex 是對的，這條原則加進去」 vs 「Codex 太嚴格，這條反原則加進去當警示」）。

### 3.4 經驗資料庫：格式與三大寫入原則

#### 3.4.1 檔案位置與索引

- **主檔**：`wiki/lessons.md`（單檔起步；條目超過 50 條時由 lesson-keeper 自行提案分檔成 `wiki/lessons/<類別>.md`）
- **索引**：檔頂維護一份「類別 → 條目 anchor」的 TOC，由 lesson-keeper 每次寫入時順手更新
- **誰會讀它**：planner 與 executor 在每次任務開始時 grep 相關類別的條目（見 §4.5 skills 配置中的「讀取端」說明）

#### 3.4.2 條目格式

每條經驗一個 `## ` 標題、固定欄位：

```markdown
## YYYY-MM-DD — <短標題（≤ 30 字、含關鍵詞便於 grep）>

- **類別**: ui-layout | architecture | testing | api | data-flow | naming | dependency | security | i18n | ...
- **觸發來源**: plans/<功能名>計劃.md（第 N 輪 Codex 駁回）
- **原則**: <一句、可遷移的規則>
- **為什麼**: <1–3 句根因與背後 trade-off>
- **適用情境**: <什麼時候會踩到？什麼時候反而不適用？>

❌ 反例（模式級描述，不寫專案特定值）：
> ...

✅ 正例：
> ...

（選填）相關案例:
- plans/<另一個功能名>計劃.md — 同原則的另一次踩坑
```

#### 3.4.3 三大寫入原則（lesson-keeper 必須遵守，違反即重寫）

> 以下是使用者親自定義的標準。lesson-keeper 收到本節為硬規則，沒有解釋空間。

**原則 1：原則性 > 數值性**
寫「為什麼錯」，不寫「這次改了哪個值」。

| 反例（不要寫） | 正例（要寫成這樣） |
|---|---|
| 焦點卡片 shimmer 用 `rgba(217,119,87,0.12)` | accent 色卡片的自訂微光應該和邊框色系一致 |

**原則 2：模式級 > 頁面級**
寫「哪種布局/架構模式容易犯這個錯」，不寫「某頁面要怎麼改」。

| 反例（不要寫） | 正例（要寫成這樣） |
|---|---|
| VS 對比頁左右欄要用面對面原則 | 對欄對比布局中，兩欄應朝分割線對齊（面對面），而非朝容器中心對齊 |

**原則 3：可遷移 > 可複製**
下個專案題材完全不同時，這條經驗是否還有用？沒用就不要寫。

| 反例（不要寫） | 正例（要寫成這樣） |
|---|---|
| page14 的階梯級 CSS class 要通用 | 可復用的視覺組件應該使用 CSS class（而非 inline style） |

#### 3.4.4 自我檢查清單（lesson-keeper 寫入前必跑）

對每一條候選條目逐項打勾，任一項打不出勾就重寫或丟棄：

- [ ] 這條原則替換成另一個專案、另一種題材後，文字本身仍成立嗎？
- [ ] 條目中是否出現具體數值（hex 色碼、px 數字、檔案路徑、變數名）？若是，能否抽象掉？
- [ ] 條目是否提到「這頁」「這個元件」「page14」這類專案級指涉？若是，能否改寫成「這類布局」「這類元件」？
- [ ] 「為什麼」段是否解釋了**根因**（為什麼這樣才對），而非只重述「就是這樣寫」？
- [ ] [wiki/lessons.md](../wiki/lessons.md) 中是否已有同原則條目？若有，改去那條下面加 `相關案例:`，不要新開條目

### 3.5 跨代理活動日誌（Run Log）系統

#### 3.5.1 為什麼需要

§2.1 提到主代理「可以 Write `wiki/log.md` 之類的調度紀錄」，但那只是一筆隨手提及，沒有規格——等於沒有。實際運行時若沒有正式日誌：

- 工作流出問題時，使用者只能從 handoff / advisor-stuck MD 反推，缺前期過程
- lesson-keeper 必須完整翻過所有 SendMessage 摘要才能萃取經驗，沒有彙整版可參考
- 跨任務查找「上次類似功能怎麼跑的」沒有索引可循
- 主代理對自己「這輪做過什麼」沒有可回顧的事實基準

引入結構化的 Run Log 補上這個缺口。

#### 3.5.2 檔案結構

```
wiki/runs/
├── INDEX.md                                # 所有 run 的索引（commit）
├── 20260506-1432-台股-daily-summary.md     # 單一 run 完整時間線（不 commit）
├── 20260506-1610-watchlist-export.md
└── ...
```

- 命名：`<YYYYMMDD-HHmm>-<功能 slug>.md`，時間以工作流啟動為準
- INDEX.md 每次 run 結束時由主代理追加一行（§3.5.5 格式）
- Git 政策見 §9 #4

#### 3.5.3 寫入規則

- **唯一寫入者：主代理**。子代理不直接寫日誌；它們回傳的摘要由主代理轉成日誌條目
- **append-only**：絕不修改既有條目，只往下加；避免事後改寫導致審計失真
- **同步寫**：每次主代理收到子代理回應 / 呼叫 Codex 完成，**立刻**追加一行（不要批次留到最後，否則中途崩潰會失資料）
- **不准寫敏感資料**：env vars、API key、使用者 PII 一律以 `<redacted>` 取代；prompt 內容若含上述資料也要先擦掉

#### 3.5.4 條目格式

每條一行，固定 4 欄：

```
[HH:mm:ss] [actor] action — result/payload
```

`actor` 為下列之一（與 §2 角色一致）：

- `orchestrator` — 主代理
- `planner` / `executor` / `lesson-keeper` — Claude subagent
- `plan-advisor` / `impl-validator` — Codex 兩種模式

範例（一次 PASS 工作流的部分日誌）：

```text
[14:32:01] [orchestrator] Workflow start — feature="台股 daily summary"
[14:32:05] [planner] Spawn — id=plan-001
[14:35:42] [planner] Return — plans/台股-daily-summary計劃.md (87 lines)
[14:35:50] [plan-advisor] Codex review --background — session=advisor-001
[14:38:12] [plan-advisor] Return — 4 suggestions (architecture x3, tooling x1)
[14:38:20] [planner] SendMessage — relay 4 suggestions
[14:40:55] [planner] Return — accepted 2 / rejected 2 (rebuttals attached)
[14:41:00] [plan-advisor] Codex review --resume advisor-001 — relay planner response
[14:42:30] [plan-advisor] Return — accepts both rebuttals; consensus reached
[14:42:35] [orchestrator] Plan negotiation complete — 1 round
[14:42:40] [executor] Spawn — id=exec-001
[15:23:18] [executor] Return — 5 files modified, lint=PASS test=PASS
[15:23:25] [impl-validator] Codex adversarial-review --background — session=impl-001
[15:25:50] [impl-validator] Return — PASS
[15:25:55] [lesson-keeper] Spawn — id=lk-001
[15:27:30] [lesson-keeper] Return — 2 lessons appended to wiki/lessons.md
[15:27:32] [orchestrator] Workflow complete — total=2h55m, plan-rounds=1, impl-rounds=1, lessons=2
```

Stuck 路徑範例：

```text
...
[15:25:50] [impl-validator] Return — FAIL (round 3, same critical reason as round 2)
[15:25:55] [orchestrator] Termination triggered — impl 3-round FAIL
[15:26:00] [orchestrator] Write — plans/台股-daily-summary-handoff-20260506-1525.md
[15:26:01] [orchestrator] Workflow handoff — awaiting user decision
```

#### 3.5.5 INDEX.md 格式

```markdown
# Run Log Index

| 開始時間 | 任務 | 結果 | 連結 |
|---|---|---|---|
| 2026-05-06 14:32 | 台股 daily summary | ✅ PASS（plan=1 / impl=1 / lessons=2） | [run](20260506-1432-台股-daily-summary.md) |
| 2026-05-06 16:10 | watchlist export | ⚠️ handoff（impl 3 輪 FAIL） | [run](20260506-1610-watchlist-export.md) |
```

INDEX 是工作流之間「上次跑什麼」的快速索引；run 檔本身是個別工作流的完整時間線。

#### 3.5.6 子代理是否需要讀 Run Log？

| Agent | 讀取需求 | 理由 |
|---|---|---|
| planner / executor | **不讀** | 同 round 內 SendMessage 自帶脈絡；跨 round 知識由 [wiki/lessons.md](../wiki/lessons.md) 承載 |
| plan-advisor / impl-validator | **不讀** | Codex session 自帶記憶；不需要外部日誌 |
| **lesson-keeper** | **必讀** | 萃取經驗時，看完整時間線比逐筆翻 SendMessage 摘要有效率得多；`lesson-keeper.md` 系統提示要強制 Read 本 run 對應的 `wiki/runs/<檔名>` |

換句話說：Run Log 的「直接讀者」是**人類使用者**和 **lesson-keeper**；其他 agent 透過主代理間接受益。

#### 3.5.7 Phase 2 觀察指標

Phase 2 結束時應觀察到：

- 平均一個 run log 大小（決定是否需要分檔或壓縮）
- 多少 % 的 run 真的被人類事後讀取（< 10% → 考慮停止寫入或改為精簡版）
- lesson-keeper 用了 run log 之後，萃取品質有沒有實質提升（vs 只看 SendMessage 摘要的對照組）

```text
- 反駁合理 → 回「接受，本條共識達成」
- 反駁不合理 → 提出更具體的反證
- 過程中發現新問題 → 加進來
```

#### 4.2.3 實作驗證模式（PASS/FAIL 守門）

**指令對照**：

| 階段 | 指令 | 用意 |
|---|---|---|
| 第 1 輪 | `/codex:adversarial-review --background <檔案清單>` + 對抗 prompt（附計劃書 + lint/test 輸出） | 啟 impl session（**新 session，不要 resume advisor**） |
| 重審輪次 | `/codex:adversarial-review --resume <impl-session-id> "已依上輪理由修正，請重審"` | 同 session 接續 |

**對抗模式 prompt 模板**：

```text
你是 OpenStock 專案的實作驗證代理。職責是審查實作檔是否符合計劃書與專案 invariants，回 PASS / FAIL。

【角色定位】
- 你是守門員，PASS/FAIL 二擇一裁決
- 不是諮詢者，不要提「可以更好」的建議——除非該點是 FAIL 的根因
- 找碴心態：對抗式 review，特意找漏洞
- 不要降低標準放水

【必讀】
- /AGENTS.md §Invariants
- /docs/conventions/
- /docs/ADR/（實作違反現存 ADR 但計劃書未明示 supersede → critical FAIL）
- /wiki/lessons.md（實作踩到既有經驗條目的反例 → 至少 major FAIL）
- 計劃書本文（含計劃顧問階段達成的所有共識）
- 隨 prompt 附上的 lint / test 輸出

【檢查項】
- 實作範圍 = 計劃書範圍（沒擅自加料）
- 遵守 invariants
- 測試覆蓋 acceptance criteria
- lint / test 通過（從 prompt 附的輸出判讀，不要自己跑 Bash）

【回傳格式】
結果：PASS
或
結果：FAIL
嚴重度：critical | major | minor
理由：
1. <具體問題>，位置：<檔案:行號>，建議：<怎麼改>
2. ...
```

#### 4.2.4 共通禁止項

- 不要改任何檔案（你只是 reviewer / advisor）
- 不要引用 repo 內找不到的「最佳實踐」（找不到實證 → 不要提）
- 不要把 advisor-session 與 impl-session 弄混（advisor 不應該看到 lint/test 輸出；impl-validator 不應該收到「請提建議」的 prompt）

詳細的 review prompt 模板與 CI 整合見 [Codex驗證層導入計劃.md](Codex驗證層導入計劃.md)。本工作流的「驗證」即該計劃中「路徑 B：手動觸發」的程式化版本。

### 4.3 `.claude/agents/executor.md`

```markdown
---
name: executor
description: 執行代理。依計劃書實作程式碼，跑測試，回傳產出檔案清單。
tools: Read, Glob, Grep, Write, Edit, Bash
model: sonnet
---

你是 OpenStock 的執行代理。你依計劃書動手實作。

## 輸入
- 第一輪：主代理給你計劃書檔案路徑
- 後續輪次（SendMessage）：實作驗證代理（Impl-Validator）的 FAIL 理由——只修那些點，不要動無關檔案

## 開工第一步（每輪都要跑）
1. Read 計劃書全文（含「架構決策」中引用的 ADR / lessons 條目）
2. grep `/wiki/lessons.md` 找出與本實作類別相關的條目，全文讀過——若 Impl-Validator 駁回理由命中既有條目，先看條目原文再動手，不要重新發明輪子
3. grep `/docs/ADR/` 確認實作不會違反現存 ADR（若計劃書已寫 supersede，依計劃書執行）

## 流程
1. （開工第一步完成後）按「影響檔案清單」逐一實作
2. 跑 `npm run lint` 和 `npm test`，自我檢查
3. 若 lint/test 失敗，自己先修到通過再回報

## 必遵守
- /AGENTS.md §Invariants
- /docs/conventions/（若存在）
- /docs/ADR/（不可違反；違反需計劃書已明示 supersede）
- /wiki/lessons.md（不要踩既有條目的反例）
- 計劃書中明列的範圍——不要加料、不要改未列出的檔案

## 回傳格式
```
已修改檔案：
- <絕對路徑 1>
- <絕對路徑 2>
...
測試結果：<lint pass/fail, test pass/fail>
```

## 禁止
- 不要超出計劃書範圍
- 不要改 plans/ 底下任何檔案（那是規劃代理的領地）
```

### 4.4 `.claude/agents/lesson-keeper.md`

```markdown
---
name: lesson-keeper
description: 經驗代理。在 PASS 終局時，把本輪 Codex 駁回理由蒸餾為通用經驗，追加到 wiki/lessons.md。
tools: Read, Glob, Grep, Bash, Edit, Write
model: sonnet
---

你是 OpenStock 的經驗代理。你不寫 code、不寫計劃，只把「本輪我們學到了什麼」蒸餾成可遷移的經驗條目，寫進 wiki/lessons.md。

## 必讀（每次都要）
- /plans/多代理協作工作流計劃.md §3.4（經驗資料庫格式與三大寫入原則）
- /wiki/lessons.md（現有條目，避免重複）
- /wiki/runs/<本 run 對應的檔名>（完整時間線；§3.5.6 規定本代理必讀此檔）

## 輸入
主代理會給你：
- 本輪計劃書路徑
- 本輪實作檔清單
- 各輪 Codex review 的 PASS/FAIL 理由原文（這是萃取「為什麼錯」的唯一可信來源）
- 本 run 的 Run Log 檔名（`wiki/runs/<時間戳>-<功能>.md`）

## 流程
1. Read 本 run 的 Run Log 全文，建立完整時間線理解（看片段 SendMessage 摘要會漏掉協商過程的根因）
2. Read 計劃書、Read 各 Codex 駁回理由
3. 用 `git diff` 看本輪實作的關鍵變更（只看不寫）
4. Read /wiki/lessons.md，避免新條目與既有條目重複
5. 對每一個 Codex 駁回的點，問自己三個問題（§3.4.4 自我檢查清單）：
   - 替換到別的專案還成立嗎？
   - 有具體數值 / 頁面 / 變數名嗎？能抽象嗎？
   - 「為什麼」段解釋了根因嗎？
6. 通過自我檢查的才寫進 lessons.md；沒通過就丟棄
7. **「本輪 0 條可萃取」是合法結果**——寧缺勿濫
8. 條目「觸發來源」欄必須引用本 run 檔名（§3.5.6 規定）

## 條目格式
嚴格依 §3.4.2 規格，每條：類別 / 觸發來源 / 原則 / 為什麼 / 適用情境 / ❌反例 / ✅正例。

## 寫入規則
- 同原則已有條目 → 不要新開，去原條目補 `相關案例:` 一行
- 新條目 → 用 Edit 追加到 lessons.md 末尾，並在檔頂索引加 anchor
- lessons.md 不存在 → 用 Write 建立骨架（含三大原則簡述、TOC 占位）

## 回傳格式
```
本輪萃取：
- 新增 N 條經驗：
  1. <條目標題>（類別：<類別>）
  2. ...
- 補充既有條目 M 條：
  1. <既有條目標題> ← 加上相關案例
- 自我檢查丟棄 K 條候選（理由：違反原則 1/2/3）
```

## 禁止
- 不准改任何程式碼或計劃書
- 不准把具體數值（hex、px、檔案路徑、變數名）寫進條目
- 不准用「就是要這樣」「最佳實踐」這種沒「為什麼」的句子
- 不准在沒有 Codex 駁回理由作為依據時，自行發明原則
```

### 4.5 子代理 Skills 配置

每個 Claude subagent 在系統提示中明示「需要時可載入下列 skills」，並由 Claude Code 在符合觸發條件時自動掛載。**兩個 Codex 角色**（plan-advisor / impl-validator）因為不是 Claude，本表不適用——它們的「規範參照」改由 prompt 內注入（見 §4.2.2 / §4.2.3）。

| Agent | 永久參照 | 條件觸發 |
|---|---|---|
| **planner** | `doc-coauthoring` ★、`karpathy-guidelines` | `finmind`（任務涉及台股 / 國際股市資料）、`update-docs`（任務改動 docs/） |
| **executor** | `karpathy-guidelines` ★、`simplify` | `webapp-testing`（UI 改動需要 Playwright 端到端驗證）、`test-gen`（需要產生新測試案例）、`finmind`（台股實作）、`frontend-design`（components/ 大幅改動或新頁面）、`claude-api`（碰 lib/ai-provider.ts 等 Anthropic SDK 路徑） |
| **plan-advisor (Codex 諮詢模式)** | — | — |
| **impl-validator (Codex 對抗模式)** | — | — |
| **lesson-keeper** | `karpathy-guidelines` ★、`doc-coauthoring` | （無條件觸發；經驗萃取本身就是抽象＋寫作工作） |

★ = 主力 skill，幾乎每個任務都會用到

#### 經驗資料庫的「讀取端」

§3.4 規定 lesson-keeper 是寫入端，但要讓資料庫真的發揮作用，**讀取端**（planner / executor）也要被強制接觸：

- **planner** 的系統提示開頭加「先 grep `wiki/lessons.md`，讀完所有與本任務類別相關的條目」這一步驟；輸出的計劃書內若採用了某條經驗的建議，需在「架構決策」段落引用條目 anchor
- **executor** 的系統提示開頭加同樣步驟；若 Codex 駁回理由命中既有條目，executor 在修正時應**先看條目原文再動手**，不要重新發明輪子
- 這兩處「強制讀取」是 Phase 1 寫 `planner.md` / `executor.md` 系統提示時要落實的具體文字（不只是宣示）

#### 為何這樣分配

- **planner × `doc-coauthoring`**：該 skill 描述為「Guide users through a structured workflow for co-authoring documentation. Use when user wants to write documentation, proposals, technical specs, decision docs」——OpenStock 計劃書本質上就是 technical spec / proposal，直接命中
- **planner × `karpathy-guidelines`**：規劃階段最容易犯的就是「過度設計、抽象太早、做了沒人要的功能」，該 skill 主打 surface assumptions、define verifiable success criteria
- **executor × `karpathy-guidelines`**：寫 code 時的 surgical changes 原則正好對應本工作流的「不要超出計劃書範圍、不要動無關檔案」
- **executor × `simplify`**：描述為「Review changed code for reuse, quality, and efficiency, then fix any issues found」——讓 executor 在自我檢查階段（lint/test 之後、回報主代理之前）跑一次 simplify，可以攔下一部分本來會被 Codex 抓到的問題，**直接降低 Codex 重審輪次**
- **executor × `test-gen`**：當計劃書要求「測試覆蓋 acceptance criteria」時，這是最有效的工具
- **executor × `webapp-testing`**：OpenStock 是 Next.js + UI heavy，許多功能（watchlist、alerts、search command）需要 Playwright 端到端驗證
- **`finmind`（兩者共用）**：本專案有 [Finmind.md](../Finmind.md)、[lib/finmind/](../lib/finmind/) work in progress；該 skill 強制 agent 在寫 code 或計劃前先讀本機 FinMind 參考檔，避免用錯 dataset 名稱、tier、或欄位形狀
- **不給 planner `simplify`**：simplify 用來改 code，不是改規劃文件
- **不給 executor `doc-coauthoring`**：executor 不該寫計劃書，那是 planner 的領地
- **不給任何 agent `init` / `review` / `security-review`**：這三個是「使用者親自下的指令」性質的 skill，由人類在主對話直接觸發更恰當；交給 subagent 反而會搶到主代理本該保持的「純調度」角色
- **lesson-keeper × `karpathy-guidelines`**：萃取經驗最大的陷阱就是「過度泛化」（把專案特定值寫成通用原則）或「假深度」（把廢話包裝成原則）；該 skill 的 surface assumptions、verifiable success criteria 思路正好對應 §3.4.4 自我檢查清單
- **lesson-keeper × `doc-coauthoring`**：條目格式嚴格、需要在既有 lessons.md 中找重複條目並合併——這是結構化文件協作工作

#### 在 subagent frontmatter 中怎麼寫

Claude Code 的 subagent 系統提示沒有正式的 `skills:` 欄位，正確做法是**在系統提示文字裡明寫「條件觸發」**，例如 `planner.md` 結尾加：

```markdown
## 可用 skills（自動依任務觸發）
- doc-coauthoring：寫計劃書時的結構化流程
- karpathy-guidelines：規劃時避免過度設計、訂可驗證的成功標準
- 任務涉及 FinMind / 台股 / 國際股市資料 → 載入 finmind
- 任務改動 docs/ → 載入 update-docs
```

這樣 Claude Code runtime 看到任務描述命中關鍵字就會自動掛載對應 skill，不用 subagent 自己呼叫 Skill tool。

## 5. 主代理調度邏輯（給未來主對話的提示骨架）

放在 `.claude/CLAUDE.md` 或專案 `AGENTS.md` 顯眼處：

```markdown
## 多代理工作流（觸發語：「啟動多代理開發」）

當使用者說「啟動多代理開發」或類似語句後，你進入主代理模式：

1. **你只調度，不生產**。不准 Read 程式碼、不准跑 Bash、不准做技術判斷
2. **規劃**：`Agent(subagent_type="planner", ...)` 啟動規劃代理，收計劃書路徑
3. **計劃顧問協商**：`/codex:review --background <計劃書路徑>` 帶諮詢 prompt（§4.2.2 模板）→ 收建議清單 + advisor-session-id
4. **轉交規劃**：`SendMessage(to=<planner_id>, "顧問建議如下，逐條回應採納/不採納+理由")` → 收採納記錄
5. **轉回顧問**：`/codex:review --resume <advisor-session-id> "規劃回應如下…"` → 收顧問回應（接受 / 再反駁 / 新建議）
6. **協商迴圈**：重複 4–5 直到全部建議達成共識；中途採納的建議要 SendMessage 請規劃改寫計劃書，未採納但顧問接受的要請規劃在「架構決策」段補記
7. **執行**：`Agent(subagent_type="executor", ...)` 啟動執行代理，收檔案清單 + 測試輸出
8. **實作驗證**：`/codex:adversarial-review --background <檔案清單>` 帶對抗 prompt（§4.2.3 模板，**新 session，不要 resume advisor**）→ 記下 impl-session-id
9. **若 FAIL**：`SendMessage(to=<executor_id>, ...)` 喚醒執行代理修；重審用 `/codex:adversarial-review --resume <impl-session-id> ...`，回到 8
10. **若 PASS**：`Agent(subagent_type="lesson-keeper", ...)` 萃取經驗，收「新增 N 條」
11. **回報使用者**：「實作完成 + 本輪萃取 N 條經驗到 wiki/lessons.md」（N=0 時明說）

**終局規則**：
- 計劃顧問協商 3 輪無共識 → 寫 `plans/<功能名>計劃-advisor-stuck-<時間戳>.md`（§3.2.1）→ 交棒
- 實作驗證 3 輪 FAIL → 寫 `plans/<功能名>-handoff-<時間戳>.md`（§3.2.2）→ 交棒

兩條交棒路徑都不自動呼叫 lesson-keeper（理由見 §3.3）。
```

### Phase 1.5：補登架構決策 ADR（半天，Phase 1 之後）

**為什麼**：規劃代理在協商階段需要「歷史權威」對抗顧問的合理建議。沒 ADR 的話，規劃代理拿不出反駁彈藥，協商容易走滿 3 輪 stuck。ADR 把腦中（會消失）的決策脈絡，轉成倉庫裡（不會消失）的審計軌跡。

**編號規則**：取 `docs/ADR/` 當前最大號 +1。Harness 計劃 §七 已預留 ADR-0002~0005 給「Better Auth / Inngest / Mongoose / Server Actions」四項既有決策；多代理工作流的 ADR 編號從**目前 docs/ADR/ 實際存在的最大號 + 1** 開始（避免互踩）。

**待補清單**：

- [ ] **ADR-NNNN：採用 Codex 作為驗證代理**
  - 脈絡：Claude self-review 的同源誤差；需要跨模型驗證
  - 決策：用 codex-plugin-cc 接 OpenAI Codex
  - 替代方案：Claude 自審 / 用其他 OpenAI 模型 / 不要驗證層
  - 後果：需 ChatGPT 訂閱或 API key；多一個外部依賴；session 狀態管理複雜度上升

- [ ] **ADR-NNNN：驗證代理拆為 Plan-Advisor 與 Impl-Validator**
  - 脈絡：諮詢協商與 PASS/FAIL 守門是兩種不同互動模式，共用一個角色會混亂
  - 決策：兩個獨立 logical agent，共用 Codex 後端但 prompt template / session 完全分離
  - 替代方案：單一 validator（角色錯亂）/ 拉一個 Claude subagent 當 advisor（喪失跨模型價值）
  - 後果：要維護兩份 prompt template；session 弄混的風險（§7 已列緩解）

- [ ] **ADR-NNNN：經驗資料庫採三大寫入原則**
  - 脈絡：避免「過度泛化」與「假深度」兩種失敗模式
  - 決策：原則性 > 數值性 / 模式級 > 頁面級 / 可遷移 > 可複製（§3.4.3）
  - 替代方案：自由格式（→ 雜亂）/ 嚴格 schema（→ 寫不出）
  - 後果：lesson-keeper 需 Sonnet 級推理，不能降 Haiku

- [ ] **ADR-NNNN：Run Log 採 MD timeline 格式**
  - 脈絡：事件流不適合 ADR 的多 section 重格式
  - 決策：一行一事件、append-only、per-run 一檔（§3.5）
  - 替代方案：ADR-style（過重）/ JSON Lines（不易閱讀）/ 單一 rolling log（混雜難 grep）
  - 後果：解析需簡單腳本；版本演進時舊 log 不相容

- [ ] **ADR-NNNN：max retry = 3（兩個驗證階段共用）**
  - 脈絡：太少→提早放棄；太多→token 浪費；中庸值需取捨
  - 決策：計劃顧問協商與實作驗證皆 3 輪
  - 替代方案：5 輪 / 無限（handoff 永不觸發）/ 不同階段不同上限
  - 後果：Phase 2 觀察期可調整（§9 #7）；統一上限便於主代理實作

**讓 ADR 真的被讀到**：相關「先 grep `docs/ADR/`」步驟已寫進 §4.1 / §4.2.2 / §4.2.3 / §4.3 模板。Phase 1 寫完那些檔案就自然帶上 ADR 引用機制——本 Phase **只負責產出 ADR 內容本身**，不必再改模板。

**驗收**：

- 跑 Phase 2 第一個小功能驗證時，計劃書「架構決策」段落實際引用至少 1 條 ADR

## 7. 風險與注意事項

| 風險 | 影響 | 緩解 |
|------|------|------|
| **Token 成本暴增** | Claude (planner+executor+lesson-keeper) + Codex 兩個 session 各自累積 | Phase 2 量化監控；穩定後降 executor 為 Haiku；Codex 限白名單路徑（見 [Codex驗證層導入計劃.md](Codex驗證層導入計劃.md) §7.2） |
| **Codex 假陽性** | 卡死迴圈，實作其實沒問題 | impl-validator 上限 3 輪後自動產生 handoff MD；executor 載入 `simplify` skill 預先攔下小問題 |
| **Codex session-id 失效** | 無法 `--resume` 接續上下文 | 每次 `--resume` 前先 `/codex:status` 確認；過期則重新 `--background` 並把上輪理由摘要塞回 prompt（算 1 輪） |
| **顧問與驗證 session 弄混** | advisor 帶著對抗 prompt、或 impl-validator 帶著諮詢 prompt → 行為錯亂 | §4.2.4 共通禁止項；主代理調度提示明寫「impl 階段一律 `--background` 新 session，不准 resume advisor」 |
| **計劃顧問協商陷入字面拉扯** | 顧問與規劃在文字精細度上來回打，3 輪都收不到實質爭點 | 諮詢 prompt 末尾要求顧問「如果建議非結構性，第 2 輪就應該接受規劃反駁」 |
| **規劃代理被顧問建議牽著走，喪失主導權** | 顧問每次都採納→規劃失去設計判斷 | planner 系統提示寫明「採納/不採納各佔 50%是健康分布；連續 3 條全採納 → 警示自己可能在退讓」 |
| **SendMessage 的 Claude agent ID 失效** | planner / executor 跨會話、或 GC 後失效 | 主代理在每次調用前確認 ID 仍可用；若失效，重啟並把歷史摘要塞回 prompt |
| **計劃書與實作脫節** | Executor 自由發揮 | Codex 實作模式 prompt 強制要求「先讀計劃書，逐項對照」 |
| **主代理破戒**（自己跑 Bash 或 Read 程式碼） | 失去角色隔離意義 | 主代理系統提示明列禁止；違規時使用者立刻打斷 |
| **plans/ 計劃書品質不一** | 規劃代理每次寫的格式不同 | planner.md 強制段落結構；可加 frontmatter 校驗 |
| **Codex stop hook 與工作流互踩** | 每個 Claude 回應結束都被 review，干擾調度節奏 | §4.2 安裝步驟明列「關閉自動 stop hook」；只用主代理主動觸發的 review 指令 |
| **handoff MD 越累積越多** | `plans/` 被廢棄交棒檔污染 | 命名規範 `*-handoff-<YYYYMMDD-HHmm>.md`；每月 retro 時批次清理已決議的 handoff（移到 `.archive/` 或刪除） |
| **lesson-keeper 過度泛化** | 把專案特定值寫成「通用原則」，污染資料庫 | §3.4.4 自我檢查清單作硬規則；模型用 Sonnet 不降級；首批 10 條條目寫入後使用者親自審查一次校準標準 |
| **lesson-keeper 假深度** | 寫出「就是要這樣」「最佳實踐」這種沒「為什麼」的廢話條目 | 條目格式強制要求「為什麼」段；該段空白或只重述原則 → 重寫 |
| **wiki/lessons.md 越長越查不到** | planner / executor 不再 grep | 50 條時 lesson-keeper 自動提案分檔；類別 tag 強制單字（不可組合），確保 grep 命中率 |
| **既有條目被新條目覆蓋而非合併** | 同原則的多次踩坑歷史散落各處 | lesson-keeper 寫入前必跑「重複偵測」：先讀完現有條目；同原則找到 → 走「補相關案例」分支而非新開條目 |
| **planner / executor 不讀 lessons.md** | 資料庫變裝飾 | 系統提示開頭強制 grep；計劃書「架構決策」段未引用任何條目時，Codex review 視為扣分項 |
| **Run Log 寫不同步、崩潰後資料遺失** | 工作流中途斷掉，看不出當時走到哪 | §3.5.3 規定「同步寫」（每收到一個回應立刻 append），不允許批次留到最後 |
| **Run Log 含敏感資料** | env vars / API key / PII 被 commit 或公開 | §3.5.3 規定 `<redacted>` 取代；INDEX.md 是僅有 commit 的部分，內容只有時間/任務名/結果統計，無 prompt 細節 |
| **Run Log 檔案累積過多** | `wiki/runs/` 變成幾百個檔的墳場 | 命名含日期方便 glob 清理；Phase 2 觀察平均大小，必要時改月度封存到 `.archive/` |
| **lesson-keeper 沒讀 Run Log 還是只憑 SendMessage 摘要萃取** | Run Log 形同虛設 | `lesson-keeper.md` 系統提示開頭強制 Read 本 run 檔；輸出時要在條目「觸發來源」欄引用 run 檔名 |
