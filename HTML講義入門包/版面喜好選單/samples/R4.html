Claude Code 使用習慣分析

資料：這台 Windows 的 43 個 session，2026-07-13 到 2026-09-16另含全域 prompt 歷史 68 則，2026-06-08 起產出日期：2026-09-17

你的使用方式很鮮明：一句話丟一個大任務，然後讓它跑幾小時到幾天。這種方式的效率取決於兩件事，第一句話有沒有把目標講清楚，以及有沒有把機械性的小事也丟給模型。資料顯示前者大致做得好，後者是最大的浪費來源。

最大的機械浪費是把對話當 git 按鈕與 App 啟動器。15 則發話只是 pull 或 push，另外 23 次用 /app-launch 啟動程式。每次都要載入約 25KB 的指令檔、跑 4 到 27 次工具呼叫，做的卻是一行終端指令就能做完的事。

方向錯誤已經很少，但剩下的都是同一種：先講方法、後講目標。問了三輪做法，才說出真正想要的結果。改用固定開場句型就能省掉那三輪。

有一個可以馬上改的小習慣。把個人資料放在檔案裡，不要直接貼進對話。

做得好的要保留：先要提案再選、把糾正寫成規則、用計劃書接力、標注 /orchestrate 的判斷 14 次裡有 13 次是準的。

值得優化的 11 個習慣

1. 拿對話當 git 按鈕

最大浪費

證據：「幫我pull和push」（7/13 三次，同一個 session 跨 35 天）、「幫我push」（8/17、8/19、8/20、8/25）、「pull」「pull」（8/20 間隔 2 分鐘）、「幫我pull」（9/6）、「幫我pull檔案」（9/7）、「幫我進行pull」（9/10）。共 15 則，11 個 session 整場只有這一句。

成本：每次要載入三份 CLAUDE.md 約 25KB 加記憶索引，再跑 4 到 27 次工具呼叫，等 1 到 3 分鐘，做的是 sh .scripts/sync.sh 一行的事。15 次合計約 4 萬 token 的指令檔重載，全部沒有產出。

改法：終端直接跑 sh .scripts/sync.sh "訊息"，或在 Git Bash 加一個 alias（第 4 節）。只有需要「幫我判斷怎麼拆 commit」時才用 /git-auto。不要為了 pull 開一個 session，更不要用一個開了 35 天的 session 當按鈕。

2. 拿 Claude 當 App 啟動器

最大浪費

證據：/app-launch 在 prompt 歷史出現 19 次、transcript 4 次；六月甚至問過「我可以規定說，以後啟用這個skill的話，要用haiku模型嗎」，表示你自己也覺得貴。

成本：每次 5 到 7 分鐘、20 到 45 次工具呼叫，只為了把程式叫起來。

改法：把啟動流程寫成 .bat 或沿用既有的 .vbs，做成桌面捷徑或開機自動啟動。skill 只留給「連不上外部服務時幫我診斷」這種需要判斷的情境。

3. 先講方法、後講目標

方向錯誤

證據：先問做法，經過兩輪示範後才說出真正的目標；另一次也是先問能有哪些成果，再說不需要播放功能。

成本：每次多兩到三輪來回，而且第一輪做的東西整個作廢。這是七月分析裡「做錯方向」痛點剩下的主要形態。

改法：需求開頭固定三行：「目標：…／我以為的做法：…／驗收：看到什麼算完成」。第一行有了，我就會直接從目標推方案，不會照你猜的方法做。
