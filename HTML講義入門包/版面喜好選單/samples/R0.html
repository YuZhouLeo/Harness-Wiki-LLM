中斷次數（七月是 17）

你的使用方式很鮮明：一句話丟一個大任務，然後讓它跑幾小時到幾天。這種方式的效率取決於兩件事，第一句話有沒有把目標講清楚，以及有沒有把機械性的小事也丟給模型。資料顯示前者大致做得好，後者是最大的浪費來源。

  • 最大的機械浪費是把對話當 git 按鈕與 App 啟動器。15 則發話只是 pull 或 push，另外 23 次用 /app-launch 啟動程式。每次都要載入約 25KB 的指令檔、跑 4 到 27 次工具呼叫，做的卻是一行終端指令就能做完的事。
  • 方向錯誤已經很少，但剩下的都是同一種：先講方法、後講目標。問了三輪做法，才說出真正想要的結果。改用固定開場句型就能省掉那三輪。
  • 有一個可以馬上改的小習慣。把個人資料放在檔案裡，不要直接貼進對話。
  • 做得好的要保留：先要提案再選、把糾正寫成規則、用計劃書接力、標注 /orchestrate 的判斷 14 次裡有 13 次是準的。

值得優化的 10 個習慣

按「省下的時間 ÷ 改起來的難度」排序。每一條都附證據、成本與具體改法。

最大浪費

1. 拿對話當 git 按鈕

證據：幫我pull和push（7/13 三次，同一個 session 跨 35 天）、幫我push（8/17、8/19、8/20、8/25）、pullpull（8/20 間隔 2 分鐘）、幫我pull（9/6）、幫我pull檔案（9/7）、幫我進行pull（9/10）。共 15 則，11 個 session 整場只有這一句。
成本：每次要載入三份 CLAUDE.md 約 25KB 加記憶索引，再跑 4 到 27 次工具呼叫，等 1 到 3 分鐘，做的是 sh .scripts/sync.sh 一行的事。15 次合計約 4 萬 token 的指令檔重載，全部沒有產出。
改法：終端直接跑 sh .scripts/sync.sh "訊息"，或在 Git Bash 加一個 alias。只有需要「幫我判斷怎麼拆 commit」時才用 /git-auto。不要為了 pull 開一個 session，更不要用一個開了 35 天的 session 當按鈕。
最大浪費

2. 拿 Claude 當 App 啟動器

證據：/app-launch 在 prompt 歷史出現 19 次、transcript 4 次；六月甚至問過我可以規定說，以後啟用這個skill的話，要用haiku模型嗎，表示你自己也覺得貴。
成本：每次 5 到 7 分鐘、20 到 45 次工具呼叫，只為了把程式叫起來。
改法：把啟動流程寫成 .bat 或沿用既有的 .vbs，做成桌面捷徑或開機自動啟動。skill 只留給「連不上外部服務時幫我診斷」這種需要判斷的情境。
方向錯誤

3. 先講方法、後講目標

證據：先問做法，經過兩輪示範後才說出真正的目標；另一次也是先問能有哪些成果，再說不需要播放功能。
成本：每次多兩到三輪來回，而且第一輪做的東西整個作廢。這是七月分析裡「做錯方向」痛點剩下的主要形態。
改法：需求開頭固定三行：「目標：…／我以為的做法：…／驗收：看到什麼算完成」。第一行有了，我就會直接從目標推方案，不會照你猜的方法做。
效率

5. Session 開著幾天不關

證據：8 個 session 超過一天。最長的 35 天只發了 4 句，全是 pull／push；5 天的那個 4 句也全是 pull；另外兩個 2.4 天的是 另一個專案 的開發 session，各 4 到 7 句。
成本：舊 session 每收一句新話都帶著整段歷史，回應變慢、費用變高，還會依過期狀態動作，例如另一台機器已經改過的檔案。開發用的長 session 在壓縮後也會忘掉早期決定。
改法：新任務開新 session。同主題要延續就 claude --resume 挑那一個，或在新 session 用 @plans/…計劃.md 接力，這是你已經在用的模式。純機械操作不要進 session。
效率

6. 檔案先丟根目錄再叫我整理，但沒有固定的收件匣

證據：9/14 把 8 張圖、2 個音檔、1 個 doc 放在 筆記庫 根目錄再叫我在 raw 和 wiki 各開一個資料夾；另一個專案 用 0905/ 資料夾當暫存；4 個 xls 與 document.pdf 也是放根目錄。
成本：做法本身很好，是你最省力的輸入方式。但沒有固定位置與固定指令，結果是根目錄散檔累積（上一份報告抓到 5 個），而且每次要重新描述「這些檔要放哪」。
改法：固定一個 _inbox/，加一個 /ingest 指令，內容就是「把 _inbox 裡的東西依 raw-capture 規則歸檔，回報清單」。以後只要丟檔加打一個指令。
效率

7. 反覆問「這台有沒有同步／設定有沒有生效」

證據：7/18 有和…同步更新了嗎、8/17 現在的資料庫的架構，跟專案中的設定有沒有一致、8/19 我的repo應該有部分進行底層設計的更新，但在這臺電腦的版本還沒有應用、8/19 skill的絕對路徑名稱可能會有失效的時候，因爲我會在另外一臺mac中執行。
成本：每次都是一輪偵查加報告，而且答案每天都會變。
改法：一個 /sync-check 指令：git fetch 與 status、全域 skill 的 --check、關鍵工具的 command -v，一行回報。開 session 先打它，或設成 SessionStart hook 自動跑。
品質

8. 專有名詞轉錄錯了才事後糾正

證據：9/7 應該是「新易盛」而非新一盛。筆記庫 裡其實有 2-wiki/法說會轉錄-術語表.md，但它是孤兒頁，MOSS-ASR 的說明書沒有引用它。
成本：錯字進了 wiki 就會被後續產出一路引用。
改法：在轉錄說明書加「轉錄前必讀術語表」一行，每次糾正後補一句「加進術語表」，讓糾正只發生一次。
小事

9. 同一則指令送出兩次

證據：8/19 18:51 與 18:53 同一段 skill 盤點長指令；9/8 00:21 同一分鐘兩次 UI 重設計指令。
成本：第二次會被排進佇列，我做完第一次後再做一次一樣的事，或把兩次混在一起。
改法：送出後等狀態列出現回應再動作。覺得卡住先看 /tasks，或按 Esc 後重送，不要直接再貼。
小事

10. /orchestrate 用在單機除錯迴圈

證據：9/16 12:08 藍牙音響重連的診斷用了 /orchestrate。這種要你重開、聽聲音、看畫面才能推進的迴圈，正是 orchestrate 規則裡寫的「嚴格單線」情境。其餘 13 次的判斷都準確。
成本：並行只放大跑腿量，瓶頸在你的耳朵時沒有幫助，還多花一輪印計畫表。
改法：記一個判準就夠：這件事拆給三個人做會不會有接縫。會，就不標注。
觀察

11. 深夜任務常寫「有問題可以再問我」，但人已經不在

證據：有問題都可以在詢問我（9/6 21:43）、有不懂的地方都可以在跟我討論（9/10 00:09）、有疑問都可以詢問我的意見（8/19 23:45）。而 55% 的發話在 23:00 到 03:59，這些 session 多半跑到早上。
成本：我真的問了，任務就停在那裡等到你醒來；我不問，又違反你的指示。
改法：睡前任務加一句「無人值守：不要問，照你的判斷做完，把假設列在最後」。白天有空盯的任務才寫「有問題問我」。
3

做得好、要保留的

先要提案，再選，再做

「先給我提議」「先給我一個 demo 的範本，然後讓我確定、選擇後，再實際修改」「請先提供給我讓我來判斷是否要添加」。這是避免整輪作廢最便宜的方法，六次都省下了重做。

把糾正寫成規則

8/17 「寫下一個全域的規則，不要將網頁放到 artifact」，同天「不要強制綁定在 windows 的路徑」變成 CLAUDE.md 的多裝置段。糾正一次就永久生效。

用計劃書接力

「幫我執行 @plans/…計劃書.md」三次，加上「請確保 plans/… 可以讓下一個 AI 無損的接著我們的對話繼續」。這是長任務跨 session、跨機器最可靠的方式。

編號子需求

8/19 的 skill 盤點 session 每一則都用 1. 2. 3. 4. 列需求，還標明哪些「直接修」、哪些「先保留」。這種寫法我幾乎不會做錯方向。

標注並行的判斷準確

14 次標注裡 13 次是批次同構或多來源調查，本來就該切。中斷從 17 次降到 2 次，「現在最新的檔案在哪裡」這個七月的痛點這兩個月一次都沒出現。

用 @ 引用檔案

19% 的發話帶 @ 或完整路徑。帶了路徑的任務我幾乎不需要偵查，這直接回答了你上一份報告問的「為什麼會讀不相關文件」。
